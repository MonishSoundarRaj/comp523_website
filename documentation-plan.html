Documentation Plan

A draft structure for the Library Navigator user guide and administrator guide, organized around the prototype’s intended readers and responsibilities.

Library Navigator

Library Navigator is a student prototype that helps people find resources offered by North Carolina public libraries. It has a public-facing reference desk and a separate staff page for managing library data. The answers and resource listings may be incomplete, so users should confirm important details with their library.

Part 1: User documentation

Intended readers

  • Patron or student: Basic web browsing skills; may be unfamiliar with library websites and online databases. The documentation should use plain language, short steps, and clear explanations of library terms.
  • Teacher or facilitator: Comfortable with a browser and guiding a student; not expected to manage administrator settings. The documentation should provide a brief introduction for read-aloud use, simple classroom activity ideas, and guidance for interpreting answers.
  • Library staff member using the public desk: Comfortable with ordinary websites; may understand library services but not this specific prototype. The guide should explain how to use the desk and how to verify resource availability without assuming they manage the data.

Quick start

  1. Enter a North Carolina ZIP code or town and choose Find my library.
  2. Ask a question in your own words, such as “Where can I find free audiobooks?”
  3. Review the answer and linked resources. Use Walk me through it when available.
  4. Check On the shelf for other listed resources, or contact the library to confirm details.

Planned sections

  1. What Library Navigator does
    • Finds library resources based on a ZIP code or town.
    • Answers questions using the resources listed for that library.
    • Shows nearby branches, library contact details, and available resources or events.
  2. For patrons and students
    • Finding a library by ZIP code or town.
    • Asking a useful question and reviewing the answer and sources.
    • Opening a resource or requesting step-by-step help.
    • Changing the selected location.
    • What to do when a ZIP code, town, answer, or link is unavailable.
  3. For teachers and facilitators
    • Short introduction that can be read aloud:
    “Library Navigator can help us explore resources our local library may offer. Enter a ZIP code or town, then ask a question. Look at the sources it gives you, and check with the library if you need to be sure a resource is available.”
    • Suggested classroom activity: choose a local ZIP code, ask about a learning or community need, and compare the answer with the linked library resource.
    • Remind students not to include names, home addresses, or other personal information in questions.
    • Explain that the prototype is for finding information and does not provide medical, legal, or financial advice.
  4. Limits and troubleshooting
    • Resource information may be incomplete or out of date; confirm with the library.
    • If the site cannot find a location, try a ZIP code or a nearby town.
    • If an answer is uncertain or the service is unavailable, check the resource list and contact the library.
    • If a link does not work, use the library’s contact information to ask for help.
  5. Optional detail
    • Brief explanations of access labels, statewide resources, staff-checked resources, and what happens when a resource requires a library card or sign-in.

Part 2: Administrator documentation

Intended reader

The administrator is an adult responsible for installing, configuring, and operating the prototype. The guide assumes they can use a terminal, install software, edit environment settings, and follow database instructions. It does not assume they are a software engineer. A separate technical document should cover code architecture and future development.

Planned sections

  1. System requirements and dependencies
    • Node.js 20.19 or newer.
    • Python 3.11 or newer and uv.
    • A Supabase project containing the expected library_data table.
    • An Anthropic API key for the Claude-backed question service.
    • A modern browser for the public site and admin page.
    • Record which operating systems and browser versions have actually been tested; the current project notes list dependencies but do not establish a tested compatibility matrix.
  2. Deployment configuration
    • Obtain the project files and install the listed dependencies.
    • Create the root .env file from the supplied example.
    • Set DATABASE_URL, ANTHROPIC_API_KEY, AI_SERVICE_TOKEN, and required administrator settings.
    • Configure ADMIN_USERNAME, ADMIN_PASSWORD, and an ADMIN_SESSION_SECRET of at least 32 characters. Leaving ADMIN_PASSWORD empty disables the admin page.
    • Keep credentials private and out of source control.
    • Run the database connection check before starting the application.
  3. Start, stop, and redeploy
    • Start the local development services using the documented project command.
    • For a deployment or restart, document the hosting environment’s process manager, required environment variables, build and start commands, health checks, and recovery steps.
    • Confirm the public desk and /admin page behave as expected after startup.
    • Document how to refresh the deployment after an update or configuration change.
  4. Accounts and access
    • Explain how administrator credentials are configured and distributed securely.
    • Describe how to change the session secret; changing it signs out current admin sessions.
    • Explain that the teacher is a user of the public desk and is not automatically the system administrator.
  5. Library data operations
    • Sign in at /admin to search, add, edit, or remove rows in library_data.
    • Explain the meaning and expected format of the data fields, with examples and a data-entry checklist.
    • Review changes before saving; confirm resource names, URLs, library or branch, and geographic scope.
    • Note that changes appear to patrons after the application refreshes its library data, typically within five minutes.
    • Clarify that the admin page manages rows; it does not create or alter database tables.
  6. Troubleshooting and recovery
    • Use the database check command to diagnose connection or table issues.
    • Include steps for missing or invalid credentials, unavailable database or AI service, failed startup, and restoring or refreshing the data.
    • Document who to contact for hosting, database, or API account issues.
  7. Compatibility and known limitations
    • Maintain a tested environment list and note known incompatibilities as they are discovered.
    • State that the library dataset may be incomplete and should be reviewed.
    • Include the consequences of disabling the admin page and of rotating administrator credentials or the session secret.

Before publication

This is a plan rather than finished manuals. Before publication, the project should fill in the tested operating systems and browsers, the production hosting and recovery procedure, and the field-by-field data-entry guidance for the actual deployment.
